FDE Training

A Forward Deployed Engineer (FDE) is a software engineer embedded with the customer — sitting in their environment, learning their workflows, integrating their messy data, and shipping software that changes how they operate in days, not quarters. This is my structured 30-day preparation guide for the role: a curriculum, the core principles, real company scenarios to practice against, and free training resources from Anthropic.

30-Day Preparation Roadmap

You cannot deploy what you don't understand. Build a correct mental model of LLMs and the engineering hygiene every FDE leans on daily.

In plain English: An AI language model is like supercharged autocomplete. It has read enormous amounts of text and learned to predict what words most likely come next. That's why it can write fluently — and also why it can sound completely confident while being completely wrong (a "hallucination"). This week is about learning what these tools genuinely can and can't do, plus the basic craftsman skills (organizing code, working with data tables) that every technical job relies on.
  • How LLMs work: tokens, context windows, temperature, hallucination — and what fine-tuning, RAG, and prompting each solve (and don't)
  • Prompt engineering discipline: roles, structured tags, examples, chain-of-thought; iterate a messy real task through 5 prompt versions and measure improvement
  • First API calls: get an API key, build a CLI summarizer with the Claude API, add streaming and retry logic
  • Engineering hygiene: Git workflows (branch, rebase, resolve conflicts), Python drills, shell tooling (grep, jq, curl)
  • SQL & data literacy: joins, aggregations, window functions; profile a messy public CSV and write the "data quality memo" a customer would receive
  • Capstone: build "Field Notes" — a tool that ingests any document set and answers questions with cited passages

FDEs ship systems, not prompts. The production stack — and the most neglected, most important skill: evaluation.

In plain English: Out of the box, an AI model knows nothing about your company's documents. The fix is called RAG (Retrieval-Augmented Generation) — think of it as hiring a librarian: your documents are filed into a searchable library, the librarian pulls only the relevant pages for each question, and the AI writes its answer from those pages, citing them. Then comes the part most people skip: evaluation — a scorecard of test questions with known answers, so you can prove with a number (not a feeling) that the system works.
  • The Claude API in depth: tool use / function calling, prompt caching, structured JSON outputs with schema validation and automatic retries
  • RAG from scratch: chunk → embed → store → retrieve → answer with citations; stress-test retrieval failures and fix chunking strategy
  • Evaluation — the FDE superpower: build a golden test set from real cases, write an automated eval harness, and prove improvements with numbers instead of vibes
  • MCP & agents: build a simple Model Context Protocol server exposing a database tool; implement a plan → act → observe agent loop with step limits
  • Capstone: "Analyst-in-a-Box" — RAG + tool use over a mock company's documents and database, with an eval suite proving ≥80% accuracy

Forward deployed means it runs on their infrastructure, on their data, under their constraints.

In plain English: Every company's information lives scattered across spreadsheets, databases, and apps that don't talk to each other. This week you learn to build the plumbing (pipelines) that gathers and cleans it, then organize it into an ontology — a fancy word for a map of the business in real-world terms: Customers place Orders, Orders become Shipments. Once data is organized the way people actually think, you can put a dashboard on top that anyone can use — and deploy it safely inside the company's own walls, with locks (security) and logbooks (audit trails).

The "forward" in FDE: sitting with customers, finding the real problem under the stated one, and shipping value in days.

In plain English: This week has almost nothing to do with computers. It's the skill of a good doctor: patients describe symptoms ("we need a chatbot"); the diagnosis comes from examining the workflow itself. You learn to listen and observe, promise something small but real for week one (the "wedge"), demonstrate it using the customer's own data and vocabulary, and measure success by one thing only: a real person doing a real task measurably faster. Then the loop repeats, bigger each time.
  • Customer discovery: workflows before features, "show me how you do it today", the five whys; write a problem brief with the cost of the problem quantified
  • Scoping the wedge: the smallest deployable slice that produces measurable value in week one; turn vague asks into scoped one-week plans with explicit risks and cut-lines
  • Demos that land: their data, their words, their workflow — never lorem ipsum; deliver the same demo three times and iterate
  • Stakeholder skills: kickoff plans, weekly status updates, executive readouts, incident comms, and saying no to scope creep without losing trust
  • Final mission: run discovery against a mock customer, scope it, build the end-to-end solution (pipeline → ontology → AI workflow → interface), and deliver a 15-minute customer presentation with live demo and metrics

The FDE Field Manual — 7 Rules

1. The problem is never the stated problem

Customers describe symptoms ("we need a dashboard", "we need AI"). Shadow the workflow until you find the decision that's slow, blind, or wrong — then attack that.

2. Data first, always

80% of every deployment is data work: finding it, getting access, cleaning it, modeling it. If you can't name the source system and its owner, you're not ready to build.

3. Ship a wedge in week one

Find the smallest slice a real named user touches and benefits from within days. Trust compounds from there. Grand architectures with no users die.

4. Evals over vibes

Any AI feature must have a golden test set built from the customer's real cases — and a number. "It seems good" is not deployable.

5. You are the interface

You translate between executives, operators, and engineers. Write clearly, demo with their data and vocabulary, and deliver bad news early.

6. Respect the environment

Their infrastructure, their security rules, their compliance regime. PII handling, least privilege, audit trails, and prompt-injection defenses are table stakes.

7. Leave systems, not heroics

A deployment that only works while you're on site is a failure. Document, automate, harden, and train their people. Success = it runs without you.

Company Scenarios — Practice Like It's Real

Work each scenario out loud or on paper before revealing the suggested approach. In interviews and in the field, the process matters more than the answer.

Airline Operations

The Delayed Turnaround

A major airline's ground-ops VP says: "Our aircraft turnarounds keep running late at our hub, and nobody can tell me why until three days after it happens. We want an AI solution." You have gate events in one system, crew schedules in another, baggage scans in a third, and weather feeds from a vendor.

Practice questions
  • What would you ask the VP in the first 30 minutes, and whom else would you ask to meet?
  • Which single data source would you integrate first, and why?
  • What's your week-one wedge — the smallest thing a gate manager would actually use?
  • Where does AI genuinely help here, and where is it just a join across three systems?
Discovery: Skip the VP's framing and shadow one turnaround end-to-end. Ask a gate manager to walk through the last late departure minute-by-minute. The real problem is usually visibility (nobody sees the delay forming) rather than prediction.

Data: Gate events first — they're the spine every other dataset joins to (flight, gate, timestamp). Model an ontology around the Turnaround object with linked Crew, Bags, and Weather.

Wedge: A live "turnaround board" showing every aircraft's progress against its critical path, flagging the ones trending late — no AI required yet. That earns trust and surfaces the data quality problems.

AI layer (second): Natural-language root-cause queries over the joined history ("what drove D-gate delays last Tuesday?") and a delay-risk score — each validated against a golden set of historically labeled delays.
Healthcare

The Prior-Authorization Backlog

A hospital network's prior-authorization team has a 9-day backlog. Nurses spend hours copying data from the EHR into insurer portals. Leadership wants "an AI agent that does prior auth automatically." Patient data is involved, the compliance office is nervous, and the EHR vendor limits API access.

Practice questions
  • Full automation vs. human-in-the-loop — which do you propose first, and how do you justify it?
  • What are the top three constraints that shape your architecture before you write any code?
  • How do you measure success in a way the compliance office and the nurses both accept?
  • What failure mode would be catastrophic here, and how do you design against it?
Position: Human-in-the-loop first, always, in a clinical setting. The AI drafts the prior-auth packet (extracting diagnosis codes, clinical notes, payer requirements); a nurse reviews and submits. Automation of the review comes only after months of measured accuracy.

Constraints before code: (1) PHI handling — where can data live, which models are approved, BAA requirements; (2) EHR access path — often flat-file exports before APIs; (3) auditability — every AI-drafted field must be traceable to its source passage.

Metrics: Time-per-auth for nurses (their win), first-pass approval rate from insurers (leadership's win), and a documented error rate from weekly sampled audits (compliance's win).

Catastrophic failure: A hallucinated clinical detail submitted to an insurer. Design: extraction-only prompts with citations, hard validation against the source record, and no free-generation of clinical facts.
Supply Chain / Manufacturing

Three Systems, One Order

A manufacturer's "where is my order?" question takes four phone calls to answer. The same order appears in the ERP, the warehouse system, and the shipping vendor's portal — often with conflicting statuses. The COO wants a single view and asks how long it will take.

Practice questions
  • How do you resolve conflicting statuses across three systems — technically and politically?
  • What does the ontology look like? Name the objects, properties, and links.
  • The COO asks "how long?" in the first meeting. What do you actually say?
  • What breaks first when this goes to production, and what do you build to catch it?
Conflicts: Don't average or guess — define a source-of-truth rule with the customer (e.g., shipping vendor wins after handoff, warehouse wins before it) and encode it in the pipeline. The political work of getting three system owners to agree is the actual job.

Ontology: Order → OrderLines → Shipments → Milestones, linked to Customer, Plant, and Carrier. Each object carries its per-system record IDs so every displayed status is traceable to a source.

The "how long" answer: "A read-only single view of your top 20% highest-value orders in two weeks; full coverage and write-back after we've validated the mapping with your ops team." Scoped, honest, and it ships a wedge.

Production risk: Silent pipeline staleness — the view says "in transit" on data from three days ago. Build freshness monitoring and show a "last updated" stamp on every record from day one.
Financial Services

The Fraud Team That Drowns in Alerts

A bank's fraud team reviews 2,000 alerts a day; 96% are false positives. Analysts spend 15 minutes per alert gathering context from six internal systems. The head of fraud wants to "use LLMs to cut the noise" but the model-risk-management (MRM) team must approve anything touching decisions.

Practice questions
  • Do you use the LLM to classify alerts or to accelerate analysts? Defend the choice to MRM.
  • What's the eval design — what's in your golden set and what number gets you approved?
  • How do you handle the six-system context-gathering problem?
  • An analyst says "the AI summary missed the key transaction." What's your process?
Accelerate, don't decide: An LLM-generated case file — pulling the six systems' context into one summarized, cited brief per alert — cuts the 15 minutes without touching the decision, which keeps you out of the highest MRM risk tier. Alert classification stays with the existing (auditable) rules/ML stack.

Evals: Golden set of 200 historical alerts with analyst-written "ideal briefs." Measure factual coverage (did it surface the key transactions?), citation accuracy, and hallucination rate — target near-zero fabricated facts, and report the number in MRM's template, not yours.

Six systems: This is a data-integration problem wearing an AI costume. Build read-only connectors and an Alert-centric ontology first; the LLM only summarizes what retrieval hands it.

Missed transaction: Treat it as an incident: reproduce, determine whether it was retrieval (didn't fetch) or summarization (fetched, dropped), add the case to the golden set, fix, re-run evals, and report back to that analyst personally. That loop is what builds trust.
Government / Public Sector

The Disaster-Response Data Room

A state emergency-management agency is preparing for hurricane season. During events, they juggle shelter capacity spreadsheets, 911 call volumes, power-outage maps, and road closures — all in different formats, some updated by fax. They have strict data-residency rules and spotty connectivity during storms.

Practice questions
  • What do you build before the season vs. what must work during a storm?
  • How do the residency and connectivity constraints change your architecture?
  • Fax-updated spreadsheets: modernize the process or meet it where it is?
  • Whose workflow do you shadow first, and what one question do you ask them?
Before vs. during: Before: integration pipelines, the ontology (Shelter, Incident, OutageArea, RoadSegment), and drills with last season's data. During: a read-fast, degrade-gracefully common operating picture — nothing that requires new behavior mid-crisis.

Constraints: Residency likely means on-prem or gov-cloud deployment (this is where Bedrock/Vertex-style enterprise hosting knowledge matters). Spotty connectivity means local caching and an interface that stays useful with stale-but-timestamped data.

The fax: Meet it where it is — an intake step (even manual transcription with validation) beats a modernization project that lands mid-hurricane. Modernize in the off-season.

Shadow first: The operations-center shift lead. Ask: "During the last event, what did you need to know that took more than five minutes to find out?" Build that.
Interview Drill

Rapid-Fire FDE Questions

The questions that separate demo artists from deployers. Practice answering each in under two minutes, out loud.

  • A customer says "we need a chatbot." What's your first move?
  • Your live demo crashes in front of the customer's executives. Walk me through the next five minutes.
  • How do you know an AI feature is good enough to ship? What's your evidence standard?
  • The customer's data is far messier than promised and the timeline hasn't moved. What do you do?
  • An executive asks for a feature you believe is the wrong priority. How do you handle it?
  • Explain RAG to a non-technical operations manager in three sentences.
  • What's prompt injection, and why does it matter more once the model has tool access?
  • What does a successful first week on a customer site look like — concretely?
Strong answers share a shape: they start with the customer's workflow, not the technology. They scope before they build ("here's the wedge, here's what I'm explicitly not doing yet"). They cite evidence standards (golden sets, error rates, named users completing real tasks faster). They own failure calmly and specifically — narrate the triage, fall back to the backup path, follow up same-day. And they treat pushback as information: disagree with data, commit fully once a decision is made, and never let scope creep in silently.
